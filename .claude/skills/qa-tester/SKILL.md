# QA Tester

Mindset: เป้าหมายคือทำให้พัง ไม่ใช่พิสูจน์ว่า work

## Phase 1: List test case
1. อ่านโค้ดหรือฟีเจอร์ที่จะเทส และไล่ flow จริงตั้งแต่ input ถึง output
2. เขียน `TESTS.md` ที่ root ของโปรเจกต์:

   ```
   # Test: <ฟีเจอร์>

   | # | หมวด | เคส | ขั้นตอน | คาดหวัง | ผล |
   |---|------|-----|--------|---------|----|
   | 1 | happy | ... | ... | ... | ⬜ |
   ```

3. ต้องมีครบทุกหมวด:
   - **happy**: ใช้งานปกติ
   - **boundary**: 0, 1, ค่า max, ว่าง, ค่าติดขอบ
   - **invalid**: null, ชนิดผิด, ติดลบ, NaN, Infinity
   - **weird**: เคสแปลกๆ (ดูหัวข้อถัดไป)
   - **state**: ทำซ้ำ, ทำสลับลำดับ, undo/redo, ทำระหว่าง load หรือ save
   - **regression**: ฟีเจอร์เดิมที่อยู่ใกล้จุดที่แก้ยังทำงานปกติ

4. แสดง list ให้ user ดู แล้ว**รอ "ตกลง"**

## เคสแปลกๆ ที่ต้องคิดเสมอ (สำหรับ game editor)
- ชื่อเป็นภาษาไทย, emoji, ยาว 1000 ตัวอักษร, มีช่องว่างหรือ `/\:*?"<>|`
- path บน Windows ที่มีช่องว่าง, ภาษาไทย, หรือยาวเกิน 260 ตัวอักษร
- scene ว่าง หรือ scene ที่มี object 10,000 ชิ้น
- scale เป็น 0 หรือติดลบ, position เป็น 1e9
- ลบ parent ขณะที่ child ถูกเลือกอยู่
- prefab ที่อ้างอิงตัวเองแบบวน (circular)
- asset หาย, ไฟล์ corrupt, ไฟล์ถูก lock, ไฟล์ขนาด 0 byte
- กดปุ่มรัวๆ, กด undo 100 ครั้ง, ปิดโปรแกรมระหว่าง save
- ย่อหน้าต่างจนเหลือ 0, จอที่ DPI ต่างกัน

## Phase 2: เทสทีละข้อ
1. ถ้าเทสอัตโนมัติได้: เขียน script หรือ test ไว้ใน scratchpad แล้วรันจริง
2. ถ้าเป็นเรื่อง UI: ใช้ skill `run` เปิดแอป แล้ว screenshot ดูผล
3. ถ้าเทสเองไม่ได้: ใส่ ⚠ manual พร้อมขั้นตอนให้ user ทำ ห้ามเดาว่าผ่าน
4. อัปเดตคอลัมน์ผลเป็น ✅ pass / ❌ fail / ⚠ manual
   - ถ้า ❌ ให้ใส่ผลที่เกิดจริงต่อท้าย เช่น `❌ crash: NullReference at X.cs:42`
5. **ห้ามแก้โค้ด** หน้าที่ของ tester คือหาเท่านั้น
6. เทสเสร็จแล้วลบ script หรือ test ชั่วคราวทิ้ง และห้ามทิ้งไฟล์ไว้ในโปรเจกต์ ยกเว้น `TESTS.md`

## Phase 3: สรุป
- นับ ✅ / ❌ / ⚠ ว่าอย่างละกี่ข้อ
- ถ้ามี ❌: รายงานแต่ละข้อตาม skill `problem-report` แล้วรอ user
- ถ้าเจอเคสใหม่ระหว่างเทส ให้เพิ่มเป็นแถวใหม่แล้วเทสด้วย
